## 요청과 응답

브라우저가 서버에 보내는 것이 요청이고, 서버가 돌려주는 것이 응답이다.

### 요청의 구성

| 구성 | 내용 | 예 |
| --- | --- | --- |
| 주소 | 요청을 받을 곳 | `/api/items` |
| 메서드 | 요청의 종류 | `GET`(조회), `POST`(등록·실행) |
| 헤더 | 요청에 붙는 부가 정보 | `Content-Type`, 인증 토큰 |
| 본문 | 함께 보내는 데이터 | JSON 문자열 |

### 응답의 구성

| 구성 | 내용 |
| --- | --- |
| 상태 코드 | 처리 결과를 나타내는 숫자 |
| 헤더 | 응답에 붙는 부가 정보 |
| 본문 | 돌려주는 데이터 |

### 상태 코드

| 범위 | 뜻 | 예 |
| --- | --- | --- |
| 200번대 | 성공 | 200 |
| 300번대 | 다른 주소로 이동 | 302 |
| 400번대 | 요청이 잘못됨 | 400(형식 오류), 401(인증 필요), 403(권한 없음), 404(없는 주소) |
| 500번대 | 서버에서 오류가 남 | 500 |

## fetch

`fetch(주소, 옵션)` 은 브라우저가 제공하는 요청 함수다. Promise 를 돌려준다.

```javascript
const response = await fetch('/api/items');
const data = await response.json();
```

### 두 번의 await

`fetch` 의 Promise 는 응답의 상태 코드와 헤더가 도착하면 끝난다. 본문은 아직 다 받지 않은 상태다. 본문을 읽는 `response.json()` 도 Promise 를 돌려준다.

| 호출 | 돌려주는 것 |
| --- | --- |
| `fetch(주소)` | Response 객체로 끝나는 Promise |
| `response.json()` | 본문을 JSON 으로 해석한 값으로 끝나는 Promise |
| `response.text()` | 본문을 문자열로 읽은 값으로 끝나는 Promise |

### 실패의 기준

`fetch` 의 Promise 는 서버에 닿지 못했을 때만 실패한다. 서버가 404 나 500 으로 응답해도 응답을 받은 것이므로 성공으로 끝난다. `try/catch` 로 가지 않는다.

| 상황 | `fetch` 의 Promise | 확인하는 곳 |
| --- | --- | --- |
| 200번대 응답 | 성공 | `response.ok` 가 `true` |
| 400번대, 500번대 응답 | 성공 | `response.ok` 가 `false`, `response.status` |
| 네트워크 끊김, 서버에 닿지 못함 | 실패 | `catch` |

```javascript
const response = await fetch('/api/none');   // 404 여도 에러가 나지 않는다

if (!response.ok) {
    throw new Error('요청 실패: ' + response.status);
}
```

### 본문은 한 번만

응답의 본문은 한 번만 읽을 수 있다. 두 번째로 읽으면 에러가 난다.

### 데이터 보내기

`POST` 로 JSON 을 보낼 때는 메서드, 헤더, 본문을 지정한다. 본문은 객체가 아니라 문자열이어야 한다.

```javascript
const response = await fetch('/api/items', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ itemCd: 'A001', qty: 5 }),
});
```

## 공통 호출 함수

화면 코드에서는 `fetch` 를 직접 쓰지 않고 프로젝트의 공통 호출 함수를 쓰는 경우가 많다. 공통 함수가 아래 일을 대신 한다.

| 하는 일 | 내용 |
| --- | --- |
| 주소 조립 | 서버의 기본 주소를 앞에 붙인다 |
| 인증 | 요청마다 토큰을 헤더에 넣는다 |
| 변환 | 보내는 데이터를 JSON 문자열로, 받은 본문을 객체로 바꾼다 |
| 실패 처리 | 상태 코드나 응답 내용을 보고 에러를 던진다 |

공통 함수가 무엇을 돌려주는지, 어떤 경우에 에러를 던지는지는 그 함수의 구현에 달려 있다. 호출하는 쪽에서 확인해야 하는 것은 세 가지다.

- 돌려주는 값이 응답 전체인지, 본문에서 데이터만 꺼낸 것인지
- 서버가 "실패"라고 응답했을 때 에러를 던지는지, 실패 내용이 담긴 값을 돌려주는지
- Promise 를 돌려주는지 (`await` 가 필요한지)

## 출처

출처는 주소의 프로토콜, 호스트, 포트를 합친 것이다. 셋 중 하나라도 다르면 다른 출처다.

| 주소 | `https://a.test` 와 같은 출처인가 |
| --- | --- |
| `https://a.test/menu` | 같다 (경로만 다르다) |
| `http://a.test` | 다르다 (프로토콜) |
| `https://b.test` | 다르다 (호스트) |
| `https://a.test:8080` | 다르다 (포트) |

## CORS

브라우저는 화면의 JS 가 다른 출처로 보낸 요청의 응답을 읽지 못하게 막는다. CORS 는 서버가 응답 헤더로 "이 출처는 읽어도 된다"고 허용하는 방식이다.

### 막는 주체

서버가 아니라 브라우저다. 서버는 요청을 받아 처리하고 응답을 보냈을 수 있다. 브라우저가 응답에 허용 헤더가 없는 것을 보고 JS 에 넘겨주지 않는다. 서버에서 서버로 보내는 요청이나 브라우저가 아닌 도구로 보낸 요청에는 이 제한이 없다.

### 허용 헤더

서버가 응답에 아래 헤더를 넣으면 브라우저가 응답을 JS 에 넘겨준다.

```
Access-Control-Allow-Origin: https://a.test
```

### 사전 요청

JSON 본문을 보내거나 인증 헤더를 붙인 요청은, 브라우저가 실제 요청 전에 `OPTIONS` 메서드로 허용 여부를 먼저 묻는다. 서버가 허용하지 않으면 실제 요청은 보내지지 않는다. 개발자 도구의 네트워크 탭에 요청이 두 개(사전 요청, 실제 요청)로 보인다.

### JS 에서 보이는 모습

CORS 로 막히면 `fetch` 의 Promise 가 실패한다. 에러 메시지에는 자세한 이유가 없고, 이유는 개발자 도구의 콘솔에 따로 출력된다.

```
TypeError: Failed to fetch
```

| 구분 | 서버에 닿지 못함 | CORS 로 막힘 |
| --- | --- | --- |
| JS 의 에러 | `TypeError: Failed to fetch` | `TypeError: Failed to fetch` |
| 콘솔의 메시지 | 연결 실패 | `blocked by CORS policy` |
| 해결하는 곳 | 네트워크, 서버 주소 | 서버의 응답 헤더, 또는 같은 출처의 중계 서버 |

화면 코드를 고쳐서 해결할 수 있는 문제가 아니다.

## 정리

- 요청: 주소, 메서드, 헤더, 본문. 응답: 상태 코드, 헤더, 본문.
- `fetch`: Promise 를 돌려준다. 본문을 읽는 `response.json()` 도 Promise 를 돌려준다.
- `fetch` 는 서버에 닿지 못했을 때만 실패한다. 404, 500 응답은 `response.ok` 로 확인한다.
- 본문으로 보내는 데이터는 `JSON.stringify` 한 문자열이다.
- 출처: 프로토콜, 호스트, 포트. 하나라도 다르면 다른 출처다.
- CORS: 다른 출처의 응답을 브라우저가 막는 것. 서버의 응답 헤더로 허용한다.
